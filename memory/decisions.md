## ADR-021
日期：2026-08-04
背景：证据 v2.0 架构（2026-07-26 部署）虽把存储集中到 `evidence/_files/`，但 `audit-execution-assistant/SKILL.md` 规则层仍教 LLM 按程序建子目录（`evidence/{project_name}/{程序编号}_{程序关键词}/`），界面示例层却用 `evidence/_files/`——规则与示例打架。`create_evidence_dirs.py` 也在一次建 74 个空程序目录。同一份证据被复制到多个程序文件夹，集中存储名存实亡。
备选方案：
- A) 保留程序目录结构，把 `_files/` 作为备份/归档层叠加
- B) 取消程序目录，全部集中 `_files/`；修 SKILL.md 矛盾；catalog 检查从"用户说帮我匹配才触发"改为 Step 1 默认动作
最终选择：B
原因：
- 程序目录结构是 v1.0 遗留，v2.0 的核心价值就是"一份证据只存一份"——保留程序目录等于否定 v2.0 本身
- SKILL.md 规则层和示例层打架是 LLM 行为不一致的根因，必须统一
- catalog 检查默认化让"证据-程序映射"成为执行时的默认动作，而非依赖用户记得喊"帮我匹配"
- `create_evidence_dirs.py` 建 74 个空目录是 v1.0 残留行为，与 v2.0 集中存储矛盾

后续：武汉长源 B1.1/L1.1 的 60 个真实证据文件按保护规则保留，finding 引用尚未迁移——待用户决策。

## ADR-026
日期：2026-08-11
背景：系统规则和脚本持续膨胀——目前已有 25 个脚本 + 14 条宪法硬约束，且每次整改都在堆叠新的防御机制。防御性堆叠本身成了新的复杂度来源：规则越来越多、脚本越来越多，反而需要更多规则去守护规则。
备选方案：
- A) 不设门槛，按需求逐个新增规则/脚本
- B) 审批制，每次新增都由用户逐一审批
- C) 纳米测试原则：新增前先自问三个问题，用"更简单的机制能否解决"过滤
最终选择：C
原因：
- 600 行教学版理念：能用更简单机制解决的不需要脚本——系统复杂度的健康标准不是"能跑"，而是"最少必要"
- 25 个脚本 + 14 条宪法已经出现防御性堆叠，新增任何东西都在加固这条链，链越壮复杂度越高
- 审批制成本过高：每次新增都打断用户，无法区分"必要的加固"和"顺手堆的防御"
- 自问三问是零成本的第一道闸：先过滤掉工程噪音，真正必要的新增才值得讨论和审批
结果：新增规则/脚本前必须过"三个自问"

## ADR-030

- 独立通道达成同样目的（新检查可见但不拦），零副作用

后续：闸机退出码缺陷记入 TODO 待修（该缺陷已于 ADR-031 修复）。

## ADR-031
日期：2026-09-10
背景：修 ADR-030 记录的闸机退出码缺陷。动手前逐行核对，**修正了 ADR-030 的诊断**——问题不是"闸机一刀切"，而是三处：
- ① 四个校验脚本（finding/report/program/policy-analysis）在"有警告无阻断"时都返回 exit 1，与"阻断"共用同一个退出码（`validate-finding.py:633`、`validate-report.py:217`、`validate-program.py:455`、`validate-policy-analysis.py:453`）
- ② `validate-report.py:210-215` / `validate-program.py:449-453` 的 `--strict` 分支**把阻断也映射成 exit 1**——所以"让闸机把 1 当警告放行"这个修法会把真阻断放过去
- ③ `validate-interview.py` 只有 0/1 两档（非 strict 时无论成败都返回 0）

备选方案：
- A) 闸机侧把 exit 1 识别为警告 —— 否决：脚本未捕获异常时 Python 也返回 1，"脚本挂了"会被当成"有警告"放行
- B) 脚本侧统一口径（有警告时返回 0）—— 否决：闸机将失去"有警告"这个信号，无法提示
- C) 闸机认三档（0=通过 / 1=打印后放行 / ≥2=拦）+ 脚本侧异常兜底 —— **采用**

最终选择：C
原因：
- 闸机保持"非 0 = 不通过"的简单契约不变，只是把"能区分"这件事实现出来
- 脚本侧顶层 try/except 把未预期崩溃转成 exit 2，堵住"崩溃伪装成警告"的入口——**这是方案 C 成立的前提，不做这步闸机就成了摆设**
- 不动 `--strict` 分支（回归基线正靠它记数），改为闸机调用时**不传** `--strict`，让 report/program 走干净的两档路径

后续：
- **替代 ADR-030 的结论**：该缺陷已修。但 `source_reconciliation` 独立通道**保留**——原文抽查本来就不该参与校验结论（它是补充信息，不是判定项），与闸机无关
- 未做（记入待办）：闸机调用 validate-program 时从未传 `--ir`，导致"覆盖率 / 判定标准 / 数据来源"三类阻断从未生效，而文档写着应传。属"加严"，与本次"松绑"分开做

## ADR-032
日期：2026-09-11
背景：新桌子补漏时把桌子格式从 1.0 升到 1.2（抽屉由三个纯名字变成 {name,path,status} 入口；新增 ingested 收料本子）。读桌子的地方原本对版本做**严格相等**判断，升版即意味着所有旧桌子一律打不开。
备选方案：
- A) 硬拒绝（保持版本不等即报错）—— 否决：1.0→1.1 的差别只是抽屉多了两个空槽，1.1→1.2 只是多一个空本子，内容完全兼容。为一处可用代码转换的差异把旧数据判死刑，等于把"版本号变了"升级成"以前的桌子全打不开"
- B) 就地升级（读的时候转换，写过一次就落成新版本）—— **采用**
最终选择：B
原因：
- 旧桌子的内容一个字节不丢，只是补齐新字段；升级发生在内存，不写盘，只读命令不产生副作用
- 实测触发点不是假想：广东长华那张真桌子就是 1.0，改前 `ledger.py show` 直接退出码 1 读不了
- 门卫（check.py）同步放宽：老版本从"拦下"改为"提醒"——它本来就有独立的结构校验（三格名、证据来源），版本号不是它判定的依据，拦报告没有道理
后续：任何再升版都要给旧版留就地升级路径；`load()` 里维护可接受的旧版本白名单。

## ADR-033
日期：2026-09-11
背景：各房间（看制度/问话/执行/举报/制度完整性）查出来的东西散在各处，只有"结论"才会进报告。补漏目标是让桌子把 16 个风险来源都收上来。调查后发现：真正有落盘格式的只有 8 类，举报线索（current-audit.json）、制度空白、控制缺口/风险点/冲突（policy-analyses）、设计观察、待查项、问题单各有一些；数据体检和大数据分析**只打屏幕或只出 result.csv，没有任何信号格式**。
备选方案：
- A) 扩写既有 `import` 命令收料 —— 否决：`import` 的设计是"老项目整桌搬家"，桌子存在即拒绝；而建项目时桌子已经开好，日常必然在"桌子已存在"状态下收料，用不了
- B) 新增 `sweep` 收料（对已存在的桌子增量并入），`import` 保留作搬家 —— **采用**
- C) 给数据体检/大数据分析先造两种信号格式再收 —— 推迟：属新任务，不在本次范围
最终选择：B
原因：
- 收料必须是**可重跑**的：同一个来源反复扫不能变两行，状态变了（"待确认"补全文件后变"已确认"）只能从这格挪到那格。做法是给桌子加 `ingested` 本子，记"哪几条是机器收的、现在挂哪"，机器只认本子里的行
- 人用 add-line/set-slot 写的字**不进本子**，所以收料一根手指都碰不到人工内容（只添不盖）
- 分格规则不另造一套分类：直接用来源自带的状态字段（已确认→确定格、待确认→信号格、涉及舞弊→红格）
后续：数据体检（DH）与大数据分析（DX）目前**接不上桌子**，因为它们根本不落盘。要接得先让那两个脚本写出信号文件，属独立任务。

## ADR-034
