# 经验教训

**本文件只写「根因 + 硬规则」**——排查过程交给 git log 与 `session.md`。
按主题分组（不按日期），同类合并；已固化成机制的注明去向，防止重犯。

## 操作类

- **Edit 的锚点要选函数体内的唯一行**——选 `def` 行会导致函数体孤立。改完即跑语法/行为校验。
- **连续提交前先看暂存区**——失败的 commit 已 `git add` 的文件会留在暂存区，被下一次 commit 悄悄带走。一单一提交。
- **shell 变量不跨调用**——PowerShell / Bash 状态不保持，长验证命令必须单条自包含。
- **glob 不支持 `|` 多模式**——多模式分开查；报"不存在"前先换一种查法交叉确认。
- **`decisions.md` / `feedback.md` 只用 Edit 追加，绝不用 Write 覆盖**（2026-07-29 曾覆盖，丢 19 条 ADR）。
- **`bump-version.py` 每次调用都推进版本号**——连跑多次 `--add` 会把版本推高，事后须核对并改回本次序号。
- **`bump-version.py --commit` 只 add VERSION.json**——要"代码改动 + 版本号同一个 commit"时别用它，改为：`bump-version.py`（不带 --commit）→ 手动 `git add` 目标文件 → 手动 `git commit -m "业务关键词"`。
- **任何涉及代码 / skill / 脚本的 commit 之前，先跑 `bump-version.py`**（纯文档 / 记忆更新不需要）。

## 验证类

- **写"已验证 / 无残留 / 全部通过"必须附可复查的证据，并写明范围**（"这 4 处已修" ≠ "全仓库无残留"）。2026-08-06 曾因验收记录假阳性，实际漏掉 44 处残留。
- **涉及删除的操作，探索阶段必须全量验证，不能抽样推断**——抽样只适用于只读分析，不适用于破坏性操作的前置确认。
- **验证循环的硬停止规则**（2026-07-10 / 07-13 两次复发后固化）：同一命令一个响应只跑一次；验证 = 执行一次 + 确认输出；汇报 = 停止；成功 = 停止；只有用户明确要求才二次验证。
- **诊断"缺什么"之前，先确认"有什么"**——读代码不能只读函数名和注释，要读参数、读 CLI 入口、读调用链。2026-07-29 曾因漏看 `--ir` 模式，误判"validate-program 只查格式"。
- **证明测试有效**（2026-09-11 起）：写出来的测试首次就是绿的，什么也证明不了。首选"事前红"（测试先跑一次看红 → 再改代码 → 看绿）；代码已改、测试是补写时才用"事后回退"。详见 `coding-safety.md` 3.3。

## 文档与代码一致性

- **写校验脚本前先读代码实际 schema**，不信任描述性文档。
- **命令写进文档前先 `--help` 实测参数形态**——`--ir` 是布尔开关而非带值参数，曾照抄方案描述写错。
- **模板类文档必须与消费它的脚本对齐验证**——模板表头缺列，按模板生成的产物必然被闸机拦下。
- **SKILL.md 及技能文档中的路径一律用相对路径**，禁写 `~/.claude` 等绝对路径（部署后文档指向会与运行环境不符）；写完 grep 检查全文无绝对路径残留。
- **memory 文件提到项目内关键文档时，必须带可定位的路径**，不能只写主题描述。
- **动目录 / 文件结构（合并 / 移动 / 删除）前，先实测物理关系**——inode、reparse point、删除联动测试。**文档写 junction ≠ 真 junction**（2026-08-12 曾因信文档假设，在多个副本间反复折腾、造成内容不一致）。

## 配置与部署

- **worktree 里的 `memory/` 是冻结的**（2026-09-14 定，用户选 A：开发分支只管代码）。做法：在 worktree 里对全部 memory 文件设 `git update-index --skip-worktree`。实测效果——本地改动 `git status` 看不见、也提交不上；而 `git merge master` **不会报错且文件内容照常跟上**（ff 合并实测通过）。因此约定：**记忆只在主目录改**；同步靠每次开发前的 `merge master`，无需手工搬。注意两点：①之后在 master 新增的 memory 文件不会自动带冻结标记，需要补设；②`git ls-files -v memory/` 里 `S` 开头的就是冻结项，出现 `H` 说明漏了。**别用 sparse-checkout 代替**——文件从 worktree 消失会让会话误判"memory 不存在"从而重新初始化一套。

- **部署到已有项目的正确流程**：`update-project.ps1` → `create_evidence_dirs.py`。工具故障不是跳过关键步骤的借口——应告知用户并等待其处理。
- **constitution 级文件修改必须 `git diff` 审查后再提交**，并保留权威文本双份（2026-08-06 曾因编辑选区错误，连带删掉 11-14 条硬约束且无删除记录）。
- **给 worker / subagent 派发任务时**：必须显式写"不要 git commit"（除非任务就是提交）；禁止绕过类操作要写"不得使用 XX"；只读型 agent 只派读类任务。

## 跨源数据

- **跨源比对编号前先归一化**——制度条款号有中文数字（"第二条"）与阿拉伯数字（"第2条"）两种写法，直接字符串比对会误报"AI 编造条款"。
- **快照闸机（R08）的正确过法**：源与快照同改（快照加 dated 注记，语义未动 + 回归绿）；**禁 SKIP 跳过**。

## 审计领域判断

- **别拿工程学的「风险必须有主」套审判发现**——报告签发时整改责任人 / 期限本应为空：责任人属**管理层回应阶段**才落定（见 `audit-execution-assistant/references/finding_schema.md` 的 `management_response` 块：`response_date` / `management_action_plan` / `target_completion_date` / `auditor_assessment`）。审计只出建议 + 建议时限，**不定责**。2026-09-11 曾据此误判 ledger 缺「关门条件」——把工程待办「无人认领会烂掉」的逻辑错搬到了审计上。
