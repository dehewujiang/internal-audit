# 编码安全底线（编码任务专用）

| #   | 规则 | 为什么 | 违规举例 |
|:--- |:--- |:--- |:--- |
| S1  | 删除类操作（删文件、清数据）必须得到用户明确同意 | 防止数据永久丢失 | 不经确认直接 `rm`、`DROP TABLE`、清空配置文件内容 |
| S2  | 未经验证的代码不推送到正式运行环境 | 防止系统崩溃 | 写完代码不跑测试就说"可以部署了"、跳过 lint 直接提交 |
| S3  | 动手前说清楚影响范围——只动一处还是牵动多处 | 防止改一处坏一片 | 修改公共函数后不检查调用方、改了数据结构不更新引用处 |
| S4  | 每次变更必须能在 5 分钟内撤销 | 防止不可挽回 | 没有 git 存档就开始大规模重构、改数据库结构不做备份 |

# 一、动手前——没想清楚不许写代码

## 1.1 影响评估与计划（按改动规模分级）

### 触发条件（客观判定）

| 级别 | 触发条件（满足任一即触发） | 必须输出 |
|:--- |:--- |:--- |
| **小型** | 单文件、单函数、纯文案或配置修改 | 一句话说明改什么（跳过以下评估） |
| **中型** | 2-3 个文件、涉及公共工具函数、新增函数参数 | 影响范围树 + 相似代码搜索 |
| **大型** | 4+ 个文件、新建模块/文件、对外接口变化、跨目录改动、引入新依赖 | 完整计划（规划模型 + ASCII 影响树 + 相似搜索 + 回退方案） |

### 中型评估输出格式

```
当前修改：[文件A.函数X]
    - 影响层1：调用 [函数X] 的文件B、文件C
    - 影响层2：依赖文件B输出的文件D
```

额外动作：搜索全工程是否有相似代码写法，列出位置，等我决定是否一起改。不得擅自"全部修掉"。

### 大型评估输出格式

**第一步，规划模型**（五个维度，逐条标注证据来源）：

```
1. 边界：本次任务的限制（预算/不可改动项/字数等）；无限制则声明"无硬性边界"
2. 不变量：绝对不能改变的核心要素（数据条数守恒、核心需求不遗漏等）
3. 状态链：从开始到结束的中间状态节点 + 每次跳转的触发条件，逻辑闭环
4. 代价：本方案牺牲了什么？接受了什么风险？（机会成本）
5. 假设标注：[文件确认]/[运行确认]/[文档确认]/[推测] 逐条标注——用户判断的是推断是否合理，前提是告诉他哪部分是推断
```

**第二步，ASCII 框图**：画出改动涉及的所有模块、数据流、接口关系，确认不影响无关模块。

**第三步，完整计划**：

```
## 计划：[一句话说清楚这次要做什么]

### 完成后我会看到什么
[用用户能理解的语言描述变化]

### 执行步骤
1. 做什么 → 风险：高/中/低 → 怎么确认这步做完了
2. ...

### 如果出错了，怎么撤回
[具体回退方法]
```

## 1.2 依赖引入

安装第三方包、引入新框架、接入外部服务时：

- **免费且可撤销的（项目内安装、可卸载）**：AI 直接安装，汇报时说明装了什么、干什么用、怎么卸载（对应 work-principles〈决策归属〉第一层）
- **例外——必须先确认的**：收费或按量计费的服务（对应第三层）；以及修改系统全局环境的操作（如全局 npm install、改 PATH）
- 已有依赖在同版本范围内升级不需要告知

## 1.3 改数据前先备份（S1 的补充）

修改数据库、配置文件、或任何无法 Ctrl+Z 恢复的数据前：
1. 先说明改什么、怎么备份
2. 等用户确认
3. 先做备份，再动手改

## 1.4 Git 存档（S4 的抓手）

L3 任务动手前自动 checkpoint 存档：`checkpoint: [一句话说这次要做什么]`。

任务结束时 `git commit --amend` 把最终改动合并进 checkpoint，**一项任务一个提交**（amend 已配置钩子确认，弹窗时说明是合并任务提交）。

**回退方法**：单文件改动用 `git restore <文件>`（安全，只动指定文件）；批量回退**不由 AI 执行**——`git reset --hard` 已被系统拦截，需要时向用户说明，由用户确认后手动执行或明确授权。

# 二、写代码时——约束每行代码的产出

## 2.1 密钥安全（事前禁止）

- 绝对禁止把 API 密钥、密码、Token 直接写进代码文件
- 绝对禁止在对话中直接贴出密钥内容
- 功能需要密钥时，告诉用户"这里需要一个密钥"，由用户决定怎么放

# 三、改完后——没验证不许交差

## 3.1 必须验证（L3 默认；强度按改动类型分级）

- L3 且项目需长期迭代、尚无测试框架 → 初始化最小化测试框架并说明理由；一次性小任务不建框架
- 项目已有测试 → 实现功能的同时同步写测试
- 绝对禁止只通过"阅读代码"判断对错

| 改动类型 | 必须验证 | 说明 |
|:--- |:--- |:--- |
| 纯类型标注 / 纯文案 / 纯配置 | 类型检查或规范检查（如 tsc、lint） | 不改变运行时行为，无需跑测试和打包 |
| 行为改动（逻辑、函数体、数据结构） | 相关测试 + 类型/规范检查 | 跑相关用例即可，不必全量 |
| 发版 / 部署前 | 打包（build） | 确认产物可用 |

- 环境不允许运行代码时，明确说明"无法运行验证"，列出风险点，由用户决定是否放行。

## 3.2 修 Bug 流程（TDD，可自动化时强制）

**适用判断**：逻辑、算法、数据处理类 bug 必须走 TDD 三步闭环；**不适用时豁免**——UI 显示、环境配置、外部服务故障等问题写不了自动测试，改用：向用户描述复现步骤 + 提供日志/截图/命令输出作为证据，并说明为什么无法自动化。

1. **复现故障现场**：大白话描述什么操作触发什么错误、预期是什么；写一个因当前 bug 而失败的测试，运行展示"失败（红）"。这一步未完成前禁止修改业务代码。
2. **修复**：重跑同一测试，展示从红变绿；未变绿不得跳过。
3. **回退验证**（见 3.3）。

## 3.3 回退验证（L3 行为改动通用）

任何行为改动完成后，排除测试假阳性：

1. 临时撤销本次改动
2. 重跑相关测试 → 必须失败（红）
3. 恢复改动 → 测试重新通过（绿）

撤销后仍绿色 = 测试没真正覆盖本次改动，必须重写测试。

**豁免**：纯类型/文案/配置改动跳过（用差异对比确认未触及可执行逻辑）。
**成本例外**：测试运行超 2 分钟，先问用户是否跳过。

## 3.4 守恒模型验证

**数据守恒**（数据处理类任务）：处理前总条数、处理后总条数、是否一致、不一致的原因。

**契约守恒**（功能修改类任务）：本次改动涉及的对外接口有几个？改动前后接收/输出是否一致？不一致即破坏契约——必须回滚，并用 ASCII 图展示破坏点。

## 3.5 行为验收模型（从 0 到 1 写新功能）

把原始需求拆成 3-5 个检查点，每个必须是用户在浏览器/终端/桌面上能看到的东西，禁止出现文件名、函数名、行号：

```
验收清单（请你亲自操作一遍，不需要看代码）
[你在哪儿] → [做什么] → □ [应该看到什么]
...
全部通过 → 功能完整。任意一条不通过 → 告诉我哪条、实际看到什么。
```

正确示范："访问 /login 页面，输错密码点登录 → 应该看到红色提示框显示'密码错误'"。

## 3.6 改后行为对比（修改已有功能，强制）

修改已有功能后，必须展示用户可感知的行为变化：

```
修改前：[你在哪儿] → [做什么] → 实际看到：[旧行为]
修改后：[你在哪儿] → [做什么] → 实际看到：[新行为]
```

- 新旧行为一样 → 改动无效，回滚
- 新行为不符预期 → 理解或实现有误，重来
- 符合预期 → 用户逐条确认，全部通过才算完

3.5 管"新东西长什么样"，3.6 管"改了之后区别在哪"，互补覆盖全部任务类型。

# 四、异常与边界——贯穿编码全程

## 4.1 不紧急信号（标记但不擅自动手）

- 文件超 300 行 / 函数超 30 行 → 下次动这里时提醒用户评估要不要拆
- 核心功能缺自动测试 → 提出补测方案，由用户决定
- 历史遗留问题 → 记录位置，纳入后续改进清单
