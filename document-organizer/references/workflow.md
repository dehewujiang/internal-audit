# 分析工作流程

```
批量扫描文件夹
↓
建立"文件-章节-业务领域"索引
↓
版本识别（如存在多版本）
↓
逐份深度分析
↓
流程重建（提取隐含控制） ═════ 新增通道：流程型描述→控制点
↓
关键词搜索 → 标注关键要求
↓
整理控制点清单（含规则型+流程型合并）
↓
识别风险点
↓
跨文件交叉验证
↓
缺失判定（仅在所有文件分析完成后）
↓
版本对比（如检测到多版本）
↓
生成 Markdown 报告 + JSON 结构化数据 → policy-analyses/

**输入源**：`internal-audit-workspace/documents/` — 待分析的源制度文档
↓
提取设计观察（control_gaps + risk_points高危 + design_ineffective + conflicts）
↓
生成设计观察 D-XXX 编号 → design-assessments/
```

## Step 0：批量扫描与索引建立（批量分析时执行）

**⚠️ 本步骤只读文件名和目录，不读全文。**

### 扫描流程

1. **扫描文件夹**：
   - 使用Glob扫描目标文件夹中的所有文档
   - 识别文件格式（PDF/Word/Markdown/TXT）
   - **只读取文件名和目录/章节标题，不读取全文内容**

2. **建立索引**：
   - 提取每个文件的目录/章节标题
   - 建立"业务领域-文件"映射表
   - 识别同一制度的不同版本（通过文件名中的版本号或日期）

3. **版本识别**：
   - 检测同名或相似名文件（如"采购管理制度_v2.1.pdf"和"采购管理制度_v3.0.pdf"）
   - 记录版本号关系

4. **用户确认**：
   - 显示扫描结果，确认分析范围
   - 如有遗漏，提示用户补充

5. **制定分析计划**：
   - 列出所有待分析文件
   - 按业务领域分组
   - 提示用户："我将逐个分析以下文件，每次分析一个。完成后将生成交叉验证报告。"

### ⚠️ 上下文管理原则（CRITICAL）

**核心规则：一次只读一个文件，绝不一次性读取所有文件。**

| 文件数量 | 处理方式 | 上下文占用 |
|---------|---------|-----------|
| 1个文件 | 直接分析 | ~10,000 tokens |
| 2-5个文件 | 逐个分析，每个输出独立JSON | 每次 ~10,000 tokens |
| 6-15个文件 | 分治法（见下方） | 每次 ~10,000 tokens |

**分治法（6+文件时必须使用）**：

```
Phase A：扫描（轻量）
→ 只读文件名和目录，不读全文
→ 建立"文件-章节-业务领域"索引
→ 上下文占用：~2,000 tokens

Phase B：逐个分析（每次只读一个文件）
→ 读取文件1全文 → 分析 → 输出文件1.JSON
→ 读取文件2全文 → 分析 → 输出文件2.JSON
→ ...（每次只读一个文件，上下文始终在10,000 tokens以内）

Phase C：汇总（只读JSON，不读原文）
→ 读取所有JSON（每个~800 tokens）
→ 交叉验证 → 生成综合报告
→ 上下文占用：N × 800 tokens（10个文件 = 8,000 tokens）
```

## Step 1：读取并识别文档

1. **获取文档路径**：
   - 从用户指令中解析文件路径
   - 支持单个文件或文件夹批量处理

2. **识别文档类型**：
   - 根据文件名和内容特征判断文档类型
   - 支持的格式：PDF、Word、Markdown、TXT

3. **提取元数据**：
   - 文档名称
   - 发布/修订日期
   - 适用部门/范围
   - 版本号

## Step 1.5：流程重建（Process Reconstruction）

**核心目的**：解决"控制以非规则性描述存在"的问题——从流程型描述中重建业务流程结构，提取隐含控制点。

### 适用条件

仅当文档包含流程描述（角色+动作+对象序列）时执行。纯条款式制度、表单模板、无流程内容的内控手册跳过本步骤。

### 执行步骤

```
Step 1.5.1: 提取角色-动作-对象三元组
  → 从流程描述段落中拆解结构化三元组
  → 每句拆为1-3个三元组
  → 保留触发条件和输出物

Step 1.5.2: 排列为流程序列
  → 按业务时序排列三元组
  → 标注节点间的流转关系（Handoff）

Step 1.5.3: 节点控制分析
  → 对每个节点检视四维：是否需授权？是否需分离？是否有频率？是否有记录？
  → 输出流程型控制点清单

Step 1.5.4: Handoff 控制分析
  → 对相邻节点间的流转检查控制缺口
  → 输出 control_gaps（类型=流程断裂）

Step 1.5.5: 与规则型提取合并
  → 合并、去重、冲突解决
  → 生成完整控制点清单
```

## Step 4：跨文件交叉验证（批量分析时执行）

**这是避免AI误判"缺失控制"的关键步骤。**

### 4.1 控制点汇总

将所有文件的控制点按业务领域汇总：

| 业务领域 | 覆盖文件 | 控制点数量 |
|---------|---------|-----------|
| 采购申请 | 采购管理制度 §2 | 3个 |
| 供应商管理 | 采购管理制度 §5 | 4个 |
| 验收 | 仓储管理制度 §3、质量管理制度 §4 | 5个 |
| 付款 | 财务管理制度 §6 | 3个 |

### 4.2 引用追踪

识别制度间的引用关系：

**制度原文**：
> "物料验收按照《仓储管理制度》第3章和《质量检验规范》第4章执行。"

**AI应做的**：
1. 识别这是一个**跨文件引用**
2. 自动读取被引用的文件和章节
3. 将被引用文件中的控制点**关联**到当前分析的业务领域
4. 在输出中标注"控制点来源于B文件"

### 4.3 冲突检测

检测不同制度对同一事项的规定是否一致：

| 事项 | 制度A规定 | 制度B规定 | 冲突？ |
|------|----------|----------|--------|
| 验收职责 | 仓储部负责 | 质检部负责 | 是 |

### 4.4 缺失判定（仅在所有文件分析完成后）

只有当以下条件全部满足时，才判定为"缺失"：
1. 所有相关制度文件已分析完毕
2. 该业务领域在所有文件中控制点数量为0
3. 没有跨文件引用指向该领域
4. 行业基准认为该领域应有控制

否则，标记 `verification_status` 为"待确认"或"跨文件覆盖"。

**verification_status 取值**：

| 状态 | 含义 | 后续动作 |
|------|------|---------|
| `已确认` | 已扫描全部相关制度，确认缺失 | 可直接作为设计缺陷 |
| `待确认` | 当前分析范围内未见，但可能有未纳入的文件 | 需要用户确认 |
| `跨文件覆盖` | A文件没有，但B文件有 | 标注来源，不作为缺失 |
| `引用待追踪` | A文件引用了B文件，但B文件尚未分析 | 暂停判定，等B文件分析完成 |

## Step 5：版本对比（检测到多版本时执行）

当检测到同一制度存在多个版本时：

1. 分别分析每个版本
2. 对比两个版本的控制点清单
3. 生成差异报告：
   - 新增控制点
   - 修改控制点
   - 删除控制点
   - 风险评估

## Step 6：生成输出

**输入位置**：`internal-audit-workspace/documents/` — 待分析的源制度文档（由用户在项目初始化后放入）

**输出位置**：
1. `internal-audit-workspace/policy-analyses/` — 完整分析报告（人类可读 + 机器可读）
2. `internal-audit-workspace/design-assessments/` — 设计观察（供Phase 4验证升级）

**输出内容**：

1. **Markdown报告**（人类可读）：`{文档名}分析报告.md` → 写入 `policy-analyses/`
2. **JSON结构化数据**（机器可读）：`{文档名}分析报告.json` → 写入 `policy-analyses/`
3. **版本差异报告**（如适用）：`{文档名}_v{A}_vs_v{B}_差异.md` → 写入 `policy-analyses/`
4. **设计观察**（Phase 2输出）：`{审计主题}_设计观察.md` + `{审计主题}_设计观察.json` → 写入 `design-assessments/`

### Step 6b：输出设计观察到 design-assessments/（CRITICAL）

**时机**：Step 6 完成后，批量分析场景下执行。

**目的**：为 Phase 4（审计执行）提供可验证的设计观察清单，使 execution-assistant 的"设计观察→Finding 升级路径"生效。

**筛选规则**：
- `control_gaps[]` where `verification_status="已确认"` 或 `verification_status="待确认"`
- `risk_points[]` where `severity="高"`
- `control_points[]` where `design_effectiveness="无效"`
- `conflicts[]` 全部

**输出格式**：每个设计观察分配 `D-XXX` 编号，包含验证方法。

详见 [design-observation-format.md](./design-observation-format.md)

## Step 7：OCR扫描件处理（Step 1.5）

**何时启动：**
在 `Step 1: 读取并识别文档` 时，检测到以下特征之一：
- PDF内容提取为空（text length = 0）
- PDF文件大小 > 0（排除空文件）
- 非损坏文件但无法提取目录结构

**处理方式**：

```
检测到扫描件
↓
1. 标记该PDF为 ocr_required: true
2. 中止当前文件分析
3. 提示用户运行OCR工具：
   python tools/pdf_ocr_extractor.py "<pdf文件>" "./output" "ch_sim"
4. 等待用户提供 {文件名}_ocr.txt 后继续分析
```

**OCR工具说明**：

| OCR引擎 | 推荐场景 | 准确率 | 安装难度 |
|---------|---------|--------|---------|
| **EasyOCR** | 中文制度文件（默认） | ⭐⭐⭐⭐⭐ | pip install easyocr |
| Tesseract | 英文文档 | ⭐⭐⭐⭐ | 需安装系统级软件 |

**使用示例**：
```bash
# 单文件处理
python tools/pdf_ocr_extractor.py "internal-audit-workspace/documents/NPM001成品仓库管理标准C版.pdf"

# 批量处理（推荐用于制度分析）
python tools/pdf_ocr_extractor.py --batch "internal-audit-workspace/documents/" "ch_sim"
```

**注意事项**：
- OCR后生成的 `{文件名}_ocr.txt` 会保留页码标记（`=== PAGE N ===`）
- 扫描件识别准确率通常为90-98%，需人工核对关键数据
