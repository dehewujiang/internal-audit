# 流程重建与隐含控制提取（Process Reconstruction）

> **引擎说明**：本文件定义了 document-organizer 在分析制度文档时，如何从**流程型描述**中系统性地重建业务流程并识别隐含控制点。解决"控制以非规则性描述存在"——即控制嵌入在流程叙述中而非声明式语句——的问题。
>
> **设计定位**：与 `control-points.md` 的关键词+语义匹配方法**并行使用**，形成双通道控制提取。

---

## 核心原理

企业制度文档存在两种控制表达模式：

| 表达模式 | 特征 | 文本示例 | 原提取方法 |
|---------|------|---------|-----------|
| **规则型**（Rule-based） | 使用控制语言关键词，语句结构为"条件+动作" | "金额超过5万元需总经理审批" | ✅ 关键词匹配即可 |
| **流程型**（Process-embedded） | 控制嵌入在业务描述中，无显性控制关键词 | "材料到厂后仓库核对送货单签收入库" | ❌ 依赖LLM偶然语义理解 |

流程重建的核心思路是：**不直接找控制，先重建业务流转结构，再在每个节点上问"这个地方需要什么样的控制？"**。

```
制度原文 → 提取(角色-动作-对象)三元组 → 排列为流程序列
          → 逐节点检视控制含意 → 识别隐含控制
          → 与规则型提取合并去重 → 完整控制点清单
```

---

## Step 1：提取角色-动作-对象三元组

### 操作方法

阅读制度原文中描述业务流程的段落，从中提取结构化三元组。

**三元组定义**：

| 要素 | 含义 | 示例 |
|------|------|------|
| **角色**（Actor） | 执行动作的主体（部门/岗位/人） | 仓库管理员、质检部、财务部 |
| **动作**（Action） | 执行的操作（动词） | 核对、签收、填写、通知、盘点 |
| **对象**（Object） | 操作作用的对象 | 送货单、采购订单、入库单、来料 |
| **触发条件**（Trigger） | 动作启动的前提或时机（可选） | 材料到厂后、每月末 |
| **输出物**（Output） | 该节点的书面产出物（可选） | 签收记录、入库单（一联财务、一联留存） |

### 提取规则

1. **一句一拆**——每句话拆解为 1-3 个三元组，不合并多句为一个大组
2. **角色优先**——优先提取显性角色（"仓库管理员"），无显性角色时从上下文推断（"办理出库"→推断角色）并标注`【推断】`
3. **动作精确**——使用原文动词，不归纳为"处理""操作"等泛化动词。比对时可合并同类，提取时保持原文
4. **保留条件**——触发条件（"每月末""材料到厂后"）独立保留，不淹没在动作描述中
5. **输出物不遗漏**——"一联交财务、一联留存"这类信息容易被 LLM 忽略，强制提取

### 示例

**制度原文**：
> 材料到厂后，仓库管理员核对送货单与采购订单，确认无误后签收入库，同时通知质检部取样检验。入库单由仓库管理员填写，一联交财务，一联留存。每月末财务部派人到仓库共同盘点。

**提取的三元组**：

```
[触发: 材料到厂后]
角色: 仓库管理员 | 动作: 核对 | 对象: 送货单与采购订单 | 输出: —

[触发: 核对无误后]
角色: 仓库管理员 | 动作: 签收 | 对象: 货物 | 输出: 签收记录

[触发: 签收同时]
角色: 仓库管理员 | 动作: 通知 | 对象: 质检部 | 输出: —
角色: 质检部 | 动作: 取样检验 | 对象: 来料 | 输出: 检验报告

[触发: 签收入库后]
角色: 仓库管理员 | 动作: 填写 | 对象: 入库单 | 输出: 入库单(一联财务, 一联留存)

[触发: 每月末]
角色: 财务部 + 仓库管理员 | 动作: 盘点 | 对象: 库存 | 输出: 盘点报告
```

## Step 2：排列为流程序列

将提取的三元组按业务时序排列，形成完整的流程链路。

### 流程可视化

用箭头表示流转方向：

```
材料到厂
  ↓
仓库管理员 → 核对 → 送货单与采购订单
  ↓ (核对无误)
仓库管理员 → 签收 → 货物
  ├→ 通知 → 质检部 → 取样检验 → 来料 (→ 检验报告)
  └→ 填写 → 入库单 (一联财务, 一联留存)
  ↓
(每月末) 财务部 + 仓库管理员 → 盘点 → 库存 (→ 盘点报告)
```

### 关键分析对象

| 分析对象 | 含义 | 重点关注 |
|---------|------|---------|
| **节点**（Node） | 一个完整的角色-动作-对象组合 | 每个节点是否缺少必要的控制要素 |
| **流转**（Handoff） | 从节点A的输出到节点B的输入 | 流转过程中是否存在信息传递断点或职责混淆 |
| **旁支**（Branch） | 同一触发条件下的多路径 | 不同路径是否有一致的控制标准 |

---

## Step 3：节点控制分析

对流程序列中的**每个节点**，从四个维度检视隐含控制：

### 检视矩阵

| 检视问题 | 命中条件 | 对应的控制类型 | 输出条件 |
|---------|---------|--------------|---------|
| 这个动作是否需要特定的授权才能执行？ | 动作涉及"核对""确认""批准""审核"性质的操作；或对象涉及资金/资产/重要数据 | 审批权限控制（AP） | 即使原文未写"审批"，只要动作性质属于核准类，即隐含审批控制 |
| 这个动作和前后动作是否可由同一人执行？ | 相邻两个节点 A→B 的角色相同，但 A 的执行结果需要独立验证（如"仓库管理员→收货"和"仓库管理员→做账"） | 职责分离控制（SS） | 对角色相同但逻辑上应分离的相邻节点，标注"潜在职责集中风险" |
| 这个动作是否有明确的触发条件或执行频率？ | 节点有频率标注（"每月"）或条件标注（"当...时"），但在流程序列中该频率/条件的执行无独立验证机制 | 定期检查控制（RC） | 有频率但无独立验证者，标注控制但不降级 |
| 这个动作是否有书面输出物？输出物的流转是否完整？ | 节点有输出物（单据、记录、报告），但输出物是否有下一步接收方不明确 | 文档记录控制（DR） | 即使原文未写"记录"二字，只要有产出物即有记录控制 |

### 决策逻辑

```
对每个节点，逐条问四个问题：
  → 全部为"否"：该节点无隐含控制，标记"纯操作节点"
  → 至少一个"是"：提取为流程型控制点，标注来源为【流程重建】
  → 与规则型提取结果冲突（同一节点两种方法得出不同控制类型）：
    → 以规则型提取为准（显性规则优先级高于隐含推断）
    → 在 control_points JSON 中标注 conflict_resolved_by="rule-based"
```

### 示例 — 对上述流程的节点分析

| 节点 | 需授权？ | 需分离？ | 有频率？ | 有记录？ | 提取的控制点 |
|------|---------|---------|---------|---------|------------|
| 仓库→核对→送货单/采购订单 | ✅ 核对属于核准性质 | ❌ 单一节点 | ❌ | ❌ | 【AP-流程重建】仓库管理员核对送货单与采购订单，隐含审批控制 |
| 仓库→签收→货物 | ❌ | ❌ | ❌ | ✅ 签收隐含记录 | 【DR-流程重建】签收动作应形成书面记录 |
| 质检→取样检验→来料 | ❌ | ✅ 仓库≠质检 | ❌ | ✅ 检验报告 | 【SS-流程重建】仓库收货与质检取样分属不同岗位 |
| 财务+仓库→盘点→库存 | ❌ | ✅ 财务≠仓库 | ✅每月末 | ✅盘点报告 | 【RC-流程重建】每月末盘点（规则型已覆盖）【SS-流程重建】财务监盘（规则型可能遗漏） |

## Step 4：Handoff 控制分析

节点分析解决"单个节点上有什么控制"。Handoff 分析解决"节点之间需要什么控制"。

### 分析范围

对流程中每两个相邻节点之间的**流转**进行检视：

```
节点A → [Handoff: 信息/实物/单据从A传递到B] → 节点B
```

### 检视问题

| 检视问题 | 含义 | 示例 |
|---------|------|------|
| 流转物是什么？ | 从A到B传递了什么（信息、实物、单据、审批结果） | 签收后的货物→质检；入库单→财务 |
| 流转物是否需要签收确认？ | 接收方是否需要确认收到 | 财务收到入库单是否需要签字确认 |
| 流转物是否可被篡改？ | 传递过程中是否存在篡改风险 | 纸质入库单在传送中可能被涂改 |
| A和B是否可兼任？ | 是否存在A做B也能做、导致职责混淆的可能性 | 仓库做账、财务也做账 |
| 流转是否有系统记录？ | 流转过程是否有系统日志或痕迹 | 入库单传递是否有系统流转记录 |

### 输出示例

```
Handoff: 仓库→财务 (入库单传递)
  流转物: 入库单(一联)
  需签收确认? 否 → 控制缺口: 财务收到入库单无签收确认
  可被篡改? 是(纸质单据) → 控制缺口: 纸质入库单在传递中可被涂改
  兼任风险? 否(仓库≠财务)
  系统记录? 否(未提及系统) → 控制缺口: 无系统流转记录
```

Handoff 分析输出的控制缺口，输出为 `control_gaps`（类型=流程断裂），不走 `control_points`。

## Step 5：与规则型提取合并

### 合并逻辑

```
规则型控制点清单（从 control-points.md 方法产出）
  +
流程型控制点清单（从本文件 Step 3 产出）
  +
Handoff 分析产出的 control_gaps
  ↓
合并去重 + 冲突解决 → 完整控制点清单
```

### 冲突解决策略

| 冲突类型 | 处理方式 |
|---------|---------|
| 同一控制点被两种方法都识别 | 保留一个，在 `source` 字段标注 `【规则型+流程重建】` |
| 控制类型不一致 | 以规则型为准（显性规则 > 隐含推断），标注冲突解决方式 |
| 流程型识别了规则型遗漏的控制 | 保留，标注来源为 `【流程重建】` |
| Handoff 分析的 control_gaps | 独立输出，不合并到 control_points |

### control_points JSON 中新增字段

```json
{
  "id": "PUR-AP-003",
  "type": "审批权限控制",
  "requirement": "仓库管理员核对送货单与采购订单后方可签收",
  "source": "第3.2条",
  "source_file": "仓储管理制度",
  "source_method": "流程重建",   // 新增：标记提取方法
  "extraction_detail": "节点分析：核对动作属于核准性质，隐含审批控制",  // 新增：推理链
  "rule_text_found": false,    // 新增：原文是否有显性控制语句
  "business_area": "存货管理",
  "design_effectiveness": "有效",
  "baseline_audit_program": { ... }
}
```

## 边界条件

| 情况 | 处理方式 |
|------|---------|
| 文档无流程描述（纯条款式制度） | 跳过流程重建，仅使用规则型提取，在分析报告备注"此文件无流程描述，已跳过流程重建" |
| 文档包含流程图 | 先按流程图提取节点，再按流程文本补充细节。流程图优先于文本 |
| 文档主要是表单模板 | 跳过流程重建，仅分析表单的控制含意 |
| 单一句子包含多处流转 | 拆分为多个三元组，不合并。如"采购员询价后填制采购申请单，部门经理审批后交总经理核准"→拆为4个三元组 |
| 流程描述缺失角色（"需办理入库手续"） | 标记角色为`【待确认】`，在 design-assessments 中输出"角色分配不明确"的设计观察 |

---

## 质量检查清单

流程重建完成后，逐项自检：

- [ ] 所有业务相关的流程段落都已拆解为三元组（无遗漏的流程段落）
- [ ] 每个三元组的角色、动作、对象都已识别（无缺失要素）
- [ ] 触发条件和输出物已提取（如有）
- [ ] 每个节点已按检视矩阵完成四维分析
- [ ] 相邻节点间的 Handoff 已检查
- [ ] 流程型控制点与规则型控制点已合并去重
- [ ] 冲突标注已解决（conflict_resolved_by）
- [ ] `source_method` 标记正确：【规则型】【流程重建】【规则型+流程重建】
- [ ] 标记为`【待确认】`的角色或节点通过了复核

## 示例：完整输出对比

**制度原文**：
> 采购员根据生产计划在 U8 系统中下采购订单，部门经理在系统中审批。订单下达后，采购员将订单传真给供应商。货物到厂后，仓管员核对实物与订单，确认无误后入库。同时通知质检部检验。入库单一联仓库存根、一联交财务。

**规则型提取结果**（现有方法）：
- AP: 部门经理审批采购订单（命中"审批"）
- DR: 入库单存根（命中"存根"）

**流程重建补充提取**（新增方法）：
- AP: 仓管员核对实物与订单（核对属于核准动作）
- SS: 采购员下单 vs 部门经理审批（虽有"审批"关键词，但职责分离含意更明确）
- SS: 仓管员入库 vs 质检部检验（收货与质检分离）
- DR: 采购订单传真给供应商（隐含发送记录要求）
- Handoff gap: 入库单从仓库到财务的传递无签收机制
- SS: 采购员下单 vs 仓管员收货（采购与收货分离）

**合并后完整清单**：
```
PUR-AP-001  部门经理审批采购订单              【规则型】
PUR-SS-001  采购员下单与经理审批职责分离       【规则型】
INV-AP-001  仓管员核对实物与订单后入库         【流程重建】   ← 新增
INV-SS-001  仓管员入库与质检部检验职责分离     【流程重建】   ← 新增
PUR-DR-001  采购订单传真发送记录              【流程重建】   ← 新增
PUR-SS-002  采购员下单与仓管员收货职责分离     【流程重建】   ← 新增
INV-DR-001  入库单存根                        【规则型】
GAP-HF-001  入库单从仓库到财务传递无签收确认   【Handoff分析】 ← 新增（control_gap）
```

**质量提升**：控制点从2个扩展到8个（含1个control_gap），覆盖了原方法遗漏的职责分离、隐含审批、文档流转等关键控制。
