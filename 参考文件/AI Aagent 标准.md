## Factor 1: Natural Language → Tool Calls

### 原作主张

LLM 作为意图解析器，将自然语言原子化地转为结构化 JSON 工具调用。确定性的代码负责执行。不要让 LLM 直接输出最终答案当结果。

### Claude Code 视角

**完全同意。** 这是 agent 的定义，不是可选的。任何一个正经的 LLM agent 都这么做——LLM 输出 `function_call`，确定性代码执行，结果送回。作者把这列为第一条可能是为了和"让 LLM 直接输出文本当答案"的 naive 做法划清界限。

核心约束：**LLM 不执行，只决策。** 执行永远是代码的事。

---

## Factor 2: Own Your Prompts

### 原作主张

提示词是代码的一等公民。应该被版本控制、测试、迭代、A/B 实验。不外包给黑盒框架——如果你不知道 prompt 里有什么，出问题时你无法定位是 prompt 问题还是逻辑问题。

### Claude Code 视角

**方向完全正确，但执行有现实困难。**

坦白说，目前行业里没有成熟的 prompt 测试方法论。你怎么给 system prompt 写单元测试？跑 100 次看成功率——成本太高。用另一个 LLM 当 evaluator——evaluator 的 bias 怎么控制？

当前最务实的做法：**版本控制 + 人工 review + 少量结构化 eval case。** A/B 实验可以做，但需要定义明确的量化指标（如"程序生成环节的退修率"），而不是"感觉好不好"。

---

## Factor 3: Own Your Context Window

### 原作主张

主动构建/格式化上下文信息，最大化 token 效率与模型理解力。不要被动堆积历史消息。作者推荐用 XML 等结构化格式组织上下文。

### Claude Code 视角

**理念对，XML 不一定是好主意。**

XML 的 tag 开销占 token，对模型理解不一定比 Markdown 好。这条的核心其实是：**你塞进 context 的每一个 token，都应该是你主动选择放进去的，不是历史惯性堆积的。**

关键实践：
- 上下文分层：始终加载的 vs 按需加载的
- 历史压缩：不是截断字符，是保留关键决策点
- 信息结构化：让 LLM 一眼看出什么是当前指令、什么是背景知识、什么是历史参考

---

## Factor 4: Tools Are Just Structured Outputs

### 原作主张

工具调用本质是 LLM 输出的结构化 JSON。用简单的 switch/match 派发执行，无需复杂抽象层。不要引入 LangChain 式的 Tool 类继承体系。

### Claude Code 视角

**完全同意，且这一点是"反框架"立场最坚实的技术论据。**

`function_call` JSON → `switch(name)` → 调用对应函数。就这么简单。任何在这之上加的抽象层——Tool 基类、ToolExecutor、ToolStrategy——都是过度工程。

一个判断标准：**如果工具注册和派发的代码超过 100 行，你就过度设计了。**

---

## Factor 5: Unify Execution State and Business State

### 原作主张

执行状态（当前步骤、等待、重试）就是业务状态的元数据。单一数据源，可序列化、可恢复、可分叉。

### Claude Code 视角

**这是 12 条里最有深度的一条。

很多系统犯的错：业务状态存在数据库，执行状态在 agent 框架内部，两者不互通。agent 就不知道"我现在做到哪了"。

但作者没说透：**这个状态的 schema 设计才是难点。** "统一"不是两个词就解决了的。什么字段是业务状态，什么字段是执行状态，两者的更新时序如何保证一致性——这些才是工程问题。

---

## Factor 6: Launch/Pause/Resume with Simple APIs

### 原作主张

Agent 应像普通程序一样支持标准生命周期 API：启动、暂停、恢复、查询状态。支持 webhook 等外部触发。

### Claude Code 视角

**方向对，但对浏览器端应用有现实限制。**

Claude Code 是 CLI 工具，天然支持启停。但如果是跑在浏览器标签页里——浏览器关闭，JavaScript 线程就没了。真正的"暂停/恢复"需要状态可序列化到 IndexedDB，下次打开时从快照恢复 AgentLoop。

这不难实现，前提是 Factor 5（统一状态）先做到。

---

## Factor 7: Contact Humans with Tool Calls

### 原作主张

人类交互不是 LLM 直接输出文本，而是通过结构化的工具调用（如 `request_human_input`），支持多渠道、异步响应与审批。

### Claude Code 视角

**思路好，但当唯一渠道就过度了。**

`request_human_input` 工具让 UI 知道"现在该渲染文件选择器还是确认按钮"——这比 LLM 自由文本说"请上传文件"可靠得多。

但有个隐性代价：**它把交互模式写死了。** 如果 LLM 需要问一个不在预设类型里的问题，就没法表达。所以这条应该作为补充机制，不能替代自由文本对话。两者并存：结构化交互用于确定性收集（文件上传、确认审批），自由文本用于开放性讨论。

---

## Factor 8: Own Your Control Flow

### 原作主张

显式设计控制逻辑（循环、条件、中断、重试、摘要、审批、上下文压缩），不依赖框架的"魔法"。LLM 只在关键决策点被调用，流程主干由确定性代码驱动。

### Claude Code 视角

**12 条里最关键的一条。

核心问题是：**控制流到底放在哪？**

Claude Code 的答案：控制流 = `while true: call LLM → execute tools → feed results back`，这个循环是确定性代码。LLM 只管"在这一步做什么"。LLM 出错的 blast radius 被限制在单步内。

很多框架的问题是反过来——让 LLM 生成一个 plan 然后执行，plan 本身可能就有逻辑错误。作者说的"不要框架魔法"，翻译成工程语言就是：**不要让 LLM 管流程，让 LLM 管决策。**

#### 业务语言详解：地铁闸机模型

**一句话版**：你的 AI 审计员现在是自己看地图自己走，没人管它走到哪了。Factor 8 说的是——你应该管住它每一步的方向，而不是让它自由发挥。

##### 你现在的模式：给 AI 一本手册，让它自己跑

你给 AI 的 SKILL.md，相当于一本《操作手册》。里面写着：

> "先分析制度文件。分析完之后，生成审计程序。程序确认后，收集证据。证据够了，写 finding。finding 写好了，辩论。辩论通过，出报告。"

然后你就放手让 AI 按手册执行。

**问题在哪？** AI 可能在以下任何一步出错：

| 场景 | AI 做了什么 | 实际应该做什么 |
|------|-----------|-------------|
| 跳步 | 制度还没分析完，就开始生成程序 | 制度分析必须全部完成才能进入下一阶段 |
| 绕路 | 收集证据时发现少了个文件，AI 自己决定"跳过这个控制点" | 应该暂停，问你要不要降级这个控制点 |
| 循环 | 辩论阶段两个角色来回说了 8 轮还没结论 | 应该在第 3 轮强制收敛，输出结论 |
| 回退 | 程序生成到一半，AI 突然觉得"制度分析还不够"，回去重新分析 | 回退需要你批准，因为这意味着前面的工作成果要重做 |

**核心问题**：AI 在管流程，但 AI 不可靠。

##### Factor 8 主张的模式：地铁闸机

把流程想象成地铁站的闸机。每个闸机之间 AI 可以自由走动，但**过闸机必须刷票**。

[入口] ──闸机── [制度分析区] ──闸机── [程序生成区] ──闸机── [证据收集区] ...

- **闸机** = 你设定的硬规则（不是 AI 判断）
- **闸机之间** = AI 的自由决策空间（AI 决定具体怎么分析）
- **刷票** = 满足退出条件（制度分析产出了 15 个控制点 → 可以进下一阶段）

AI 不能跳闸机，不能绕闸机，不能自己把闸机搬开。AI 只能在两个闸机之间自由发挥。

##### 你控制什么，AI 控制什么

**你（代码）控制的事——硬规则，AI 不能改：**

- 阶段顺序：必须先分析制度，才能生成程序。不能跳
- 退出条件：制度分析阶段必须产出至少 1 份分析文件，每个控制点都标注了证据类型——满足才能进入程序生成阶段
- 回退审批：如果证据不足需要降级控制点，必须你确认，AI 不能自己降
- 辩论上限：同一 finding 最多辩论 3 轮，第 3 轮必须输出结论

**AI 控制的事——软决策，AI 自由发挥：**

- 这段制度文本里，哪几句涉及采购控制？→ AI 判断
- 这个问题应该设计成哪种审计程序？→ AI 判断
- 这份证据和 finding 之间的关系是什么？→ AI 判断

**判断标准**：这个决定需要"读懂意思"吗？需要 → AI 做。不需要 → 你写死。

## Factor 9: Compact Errors into Context Window

### 原作主张

将异常转为 LLM 能理解的紧凑结构化错误信息，注入上下文，使 Agent 具备"自愈"能力。同时需防止无限重试，需要有重试预算。

### Claude Code 视角

**实用主义的好原则，但我补充一条更根本的：验证 ≠ 错误处理（见 Factor 16）。**

结构化错误的设计要点：
- **错误分类**：可重试 vs 致命 vs 权限 vs 业务逻辑冲突
- **上下文**：什么操作、什么文件、为什么失败
- **建议行动**：LLM 收到错误后应该怎么做
- **重试预算**：还剩几次重试机会

## Factor 10: Small, Focused Agents

### 原作主张

每个 Agent 只做一件事，控制在 3-10 步（最多 20 步）。通过组合多个小 Agent 完成复杂工作流。这是原作最激进的主张。

### Claude Code 视角

**这是 12 条里我最有保留的一条。**

作者说每个 agent 只做一件事，通过组合完成复杂工作流。问题：
- **信息传递损耗**：A agent 的输出是 B agent 的输入，但 A 的中间推理过程 B 看不到
- **谁来编排？** 如果又是另一个 LLM，那只是把复杂度转移到 orchestrator 上
- **上下文切换成本**：每切换 agent，重建 system prompt + 相关历史

Claude Code 的选择是**一个主 agent + 按需 subagent**。主 agent 保有全局视角，subagent 只在明确可并行的子任务时拆分。不是平等组合，是主从架构。

作者的理由是"防止上下文窗口爆炸"——但这个问题的正解是 context 管理（Factor 3），不是拆 agent。拆 agent 是治标不治本。

**但也有道理的部分**：在成本架构上（Factor 15），小 agent 用便宜模型跑，只在关键决策点用强模型——这个角度看，拆分有经济价值。


---

## Factor 11: Trigger from Anywhere, Meet Users Where They Are

### 原作主张

支持 Slack/邮件/短信/Webhook/Cron 等多渠道触发与响应，Agent 融入用户现有工作环境。

### Claude Code 视角

**产品视角的好建议，但不是架构原则。**

对 brain_audit 这种浏览器端交互式审计工具，暂时不适用。但未来如果有"定时审计检查"或"Slack 通知审计发现"的需求，这条就相关了——前提是 Factor 6（生命周期 API）先到位。

## Factor 12: Make Your Agent a Stateless Reducer

### 原作主张

将 Agent 设计为纯函数 `(state, event) → newState`，实现函数式编程的可预测性、可测试性、并发安全。

### Claude Code 视角

**这条最"学术味"——听起来很美，工程代价大。**

(state, event) → newState， 要求每次状态变更都复制整个 state。当 state 包含 50 轮对话历史、文件系统快照、项目元数据时，复制成本不可忽略。

而且 agent 的核心 state 就是**对话历史本身**——LLM 的上下文就是它的"状态"。你没法把对话历史变成不可变 reducer，因为 LLM API 的接口本身就是可变的消息数组（messages 数组是 append-only 的可变结构）。

我的替代方案：**与其追求纯函数式，不如追求"可序列化"。**

- 状态能在任意时刻 dump 成完整 JSON
- 能从 JSON 恢复，继续执行
- 关键决策点自动保存快照
- 用户可以"回到 5 步之前，换一个决策方向"

这些能力不需要 reducer 模式也能实现。性价比更高。

## Factor 13: 工具设计是头等工程

### 原则

**工具描述的质量、参数命名的直觉性、返回值的信息密度——这些比 prompt 工程更影响 agent 行为。**

工具返回的信息不仅要确认"做了什么"，还要包含**足够上下文让 LLM 做下一步决策**。多返回 50 个 token 的上下文，可能省掉一次额外的工具调用。

### 设计标准

| 维度 | 差 | 好 |
|------|-----|-----|
| 返回值 | `"success"` | `{ status: "written", path, size, note: "相邻文件: audit-program.md, evidence-1.md" }` |
| 参数 | `path: string` | `path: string (相对于工作目录的路径，例: audit-programs/program-v1.md)` |
| 错误 | 抛异常 | 返回结构化 ToolError（见 Factor 9） |
| 副作用 | 不告知 | `{ status: "written", overwritten: true, backup_saved: "snapshots/2026-05-21T10:30:00.md" }` |

---

## Factor 14: 安全 = 工具分域

### 原则

**不同阶段用不同工具子集。任何阶段都不该拥有全部工具。**

工具越多，LLM 选正确工具的概率越低，选错工具的危害越大。把工具按阶段分域，不仅是安全，还能提高可靠性。

### 分域设计

```
审计分析阶段（只读）：  read_file + grep + glob + run_skill
证据收集阶段（读写）：  read_file + write_file + grep + glob
程序生成阶段（读+生成）： read_file + write_file + generate_excel
报告生成阶段（读+生成）： read_file + write_file + generate_excel
辩论阶段（只读+写）：    read_file + write_file
```

---

## Factor 15: 模型-任务匹配（成本架构）

### 原则

**不是所有 LLM 调用都需要最强大脑。架构决策直接影响运行成本。**

一条审计项目可能产生几十万 token 的对话。如果每个 `read_file` 的结果都喂给最强模型解读，成本会失控。

### 调用分级

```
Level 1 — 便宜模型 (Haiku/小参数)：
  - 意图分类（用户想做什么）
  - 简单文件内容总结
  - 格式检查

Level 2 — 中等模型 (Sonnet/DeepSeek-Chat)：
  - 制度分析
  - 审计程序生成
  - 证据初步评估

Level 3 — 最强模型 (Opus/DeepSeek-Reasoner)：
  - 复杂异常判断
  - 13 角色辩论
  - 最终报告生成
  - 质量闸门评估
```

---

## Factor 16: 自验证闭环

### 原则

**验证不是错误处理。验证是：agent 输出 X 之后，有没有另一条路径独立确认 X 是对的？**

错误处理是被动的（出事了才触发），验证是主动的（每次都做）。这是 agent 可靠性的核心机制，和 Factor 9（错误压缩）互补。

### 验证模式

```
写后读验证：    write_file → read_file 确认内容完整
生成后检查：    generate_excel → 检查行数/列数/公式完整性
分析后反问：    分析出"制度缺失 3 项" → 验证"制度里确实没提到这 3 项"
程序后追溯：    生成 15 条审计程序 → 逐条确认每条都能追溯到制度条款
```

### 业务语言详解：回水阀

**一句话版**：AI 写完一份文件后，有没有另一条路径独立确认它写对了？验证不是"出错后再查"，而是"每次做完都查"。

#### 用审计方法论来理解

审计的核心操作模式就是——不信任单一来源，必须交叉验证：
- 被审计方说"采购流程没问题" → 你不信，抽查 15 份采购单逐一核对
- 制度写道"供应商须经双签审批" → 你不信，去看出纳系统中的实际审批记录
- 仓库说库存盘点准确率 99% → 你不信，自盘 200 项对比差异

**你做审计，从来不会因为"他们说没问题"就写"没问题"。** AI 也需要同样的待遇。

#### 当前的问题：AI 做完就算了

```
write_file("policy-analyses/采购制度分析.json", "...") → "写入成功"
→ AI："好，分析完成了，进入下一步"
```

没有回头确认内容。问题在哪：

| AI 做了什么 | 可能出错的地方 | 没有验证的后果 |
|------------|-------------|-------------|
| 写入一份制度分析 JSON | 中途截断，只写了前 800 行 | 后续程序基于残缺分析生成，全错 |
| 生成一份 Excel 审计程序 | 15 条程序漏了 2 条 | 证据收集阶段少覆盖 2 个控制点 |
| 分析说"制度缺失 3 项控制" | AI 理解错了，制度里其实有这 3 项 | 报告中写出"制度缺陷"，被审计方拿出原文反驳 |
| 辩论后修改了 finding | 修改后的事实陈述和原始证据对不上 | finding 在法律上不可用 |

## Factor 17: LLM 和确定性代码的边界律

### 原则

**如果逻辑能用不超过 50 行代码表达，就不要让 LLM 做。**

这是判断"什么该用 LLM、什么该写代码"的经验律：
- 状态流转 → 代码状态机，不是 LLM 判断
- 文件路径拼写 → 代码模板，不是 LLM 自由发挥
- 数据格式校验 → 代码，不是 LLM
- 语义判断（政策文本是否有控制缺陷）→ LLM

**判断标准：这个决策需要理解语义吗？** 不需要 → 写代码。需要 → 调 LLM。

---

## Factor 18: 渐进式能力披露

### 原则

**LLM 看不到的东西就不会误用。**

Factor 3（掌控上下文）讲的是"管理已加载的信息"，这条讲的是"决定什么时候加载什么能力"：

```
Level 0（始终在 context）：constitution 核心约束 + about-me
Level 1（按阶段加载）：当前阶段 SKILL.md + 当前阶段工具定义
Level 2（按需加载）：references 文件 + 历史相关片段
Level 3（不加载）：其他阶段 SKILL.md、无关工具定义、无关历史
```

## Factor 19: 可观测性是头等需求

### 原则

**对于审计场景，可解释性本身就是产品功能。审计员必须能回答"这个结论是怎么得出来的"。**

| 信号 | 回答什么问题 | 对审计的特殊意义 |
|------|-------------|-----------------|
| 当前步骤 | agent 卡在哪了？ | 审计经理要知道进度 |
| token 消耗 | 项目花了多少钱？ | 项目成本核算 |
| 工具调用日志 | 读了哪些文件？写了什么？ | **审计轨迹 = 合规证据** |
| 决策点快照 | 为什么选 A 不选 B？ | 审计方法论可辩护性 |
| 延迟分解 | 是模型慢还是工具慢？ | 性能优化依据 |
| 证据链追溯 | 这个 finding 从哪条制度推导来的？ | **法律级可追溯性** |
