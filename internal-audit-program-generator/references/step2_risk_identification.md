# Step 2: 风险识别详细规范

## 2.1 基础风险框架（所有目的均执行）

基于 Step 0 读取的公司特征和审计主题，AI 自由推演风险点，按以下三类标注。**优先质量而非数量，禁止使用数量最低值约束。**

| 风险类型 | 最低事实支撑要求 | 说明 |
|---------|-----------------|------|
| **【经验类】** | 每个风险点必须描述该舞弊手法在本公司场景下的具体表现形式，不得使用通用行业描述 | 行业内已验证的舞弊/控制风险。参考 `internal_audit_risk_framework.md` 作为背景知识，简要描述，不展开 |
| **【系统类】** | 每个风险点必须引用 my-config.md 中的具体系统名称和模块，并描述该系统的哪个配置或功能点可能被利用 | 基于公司实际使用的 ERP/MES 等系统，推演该系统配置中可能被利用的风险。重点展开：系统要素、红旗信号、测试方向 |
| **【公司类】** | 每个风险点必须在 about-me.md 中有 ≥2 条独立事实作为支撑依据，且须说明每条事实与该风险之间的因果链路 | 基于 about-me.md 中公司的真实特征（规模、结构、客户、历史风险等）推演，不得使用通用描述 |
| **【制度类-设计缺陷】** | 每个风险点必须引用具体的制度编号和条款内容，不得使用"制度规定不足"等模糊描述 | 来自document-organizer JSON：design_effectiveness="无效"的控制点 + verification_status="已确认"的control_gaps + severity="高"的risk_points + conflicts。**注意：此类风险走轨道A（控制有效性测试），不走轨道B（舞弊实质性测试）** |

### 推演原则

- 每个风险必须标注来源：**【经验类】/ 【系统类-推演】/ 【公司类-推演】/ 【制度类-设计缺陷】**
- 【系统类】的推演对象是 my-config.md 中记录的**该公司实际系统**，不预设必须包含的系统名称
- 【公司类】必须能在 about-me.md 中找到对应的公司特征作为推演依据
- 【制度类-设计缺陷】直接引用document-organizer JSON中的control_gaps和design_effectiveness="无效"项，**必须**在来源标注中显示制度编号和制度名称，格式：
  - 单个制度：`【制度类-设计缺陷：CP-N001-07（NPM001成品仓库管理标准）】`
  - 多个制度（用分号分隔）：`【制度类-设计缺陷：CP-N007-06（NPM007材料仓库管理标准）；CG-N007-02（NPM007材料仓库管理标准）】`
  - **具体做法**：根据风险描述中的制度编号（如CP-N001-07），查询Step 0.3构建的映射表，获取对应的制度名称，补全到来源标注中

### 2.1.1 公司锚定（动态提取）

从 about-me.md 中提取与本次审计主题**最相关**的公司特征。所有数字直接来自 about-me.md 动态读取，不得硬编码。

## 2.2 目的自适应风险类别（按需激活）

### 仅当审计目的包含"运营效率审计"时执行：【效率类】风险识别

**核心问题**：该审计主题下，哪些环节存在资源浪费、效率低下、或与行业/公司目标存在显著差距？

基于 about-me.md 中的公司特征（产品线、生产工艺、系统配置、已知问题）和本次审计主题，**AI 自由推演**该公司在该主题下最可能存在的效率类风险，识别 **5-10 个效率类风险点**：

- 推演维度不限：可从生产、质量、库存、采购、人员、设备、能源等任意角度切入
- 每个效率风险需描述：浪费模式、可能根因、影响范围
- 所有阈值和基准来自 my-config.md 或 about-me.md 中记录的公司目标，不使用行业通用数值替代
- 每个风险标注：**【效率类-推演】**

---

### 仅当审计目的包含"合规性审计"时执行：【合规类】风险识别

**核心问题**：该审计主题下，哪些制度、行业标准或法规存在执行缺口？

基于 about-me.md 中的公司特征（产品线、客户结构、所在地区、行业认证情况）和本次审计主题，**AI 自由推演**该公司在该主题下最可能存在的合规类风险，识别 **4-8 个合规类风险点**：

- 推演层次不限：可从内部制度、行业标准、劳动法规、环保安全等任意层次切入
- 需结合公司的实际客户要求（来自 about-me.md）而非通用客户名称
- 每个合规风险需描述：缺口内容、潜在后果
- 每个风险标注：**【合规类-推演】**

---

## 2.5 跨类复合风险强制扫描（所有目的，每次必须执行）

> 不依赖任何参考文档，AI 独立执行，与审计目的无关。目的是捕捉单一主题框架天然遗漏的跨类复合风险。

### A. 跨类复合风险动态推演

**不使用预设组合清单。**

基于以下信息，AI 自由推演本次审计中可能存在的跨类复合风险：
- Step 2 已识别的风险清单（含来源标注）
- about-me.md 中的公司供应链结构、子公司关系、系统架构、历史已知风险

**推演逻辑**：
```
对 Step 2 中每一个风险，思考：
→ 这个风险如果要"藏得更深"或"造成更大损失"，
  需要在哪些其他业务领域（采购/生产/销售/资金/资产/人员）同时配合？
→ 这种跨领域配合在本公司的系统和流程中是否可能发生？
→ 形成的复合风险是否已被 Step 2 的任何风险覆盖？
```

**输出要求**：
- 列出所有推演出的跨类复合风险，标注涉及的业务类别组合
- 对 Step 2 已覆盖的组合，标注"已覆盖于 RXX"，不重复生成
- 对未覆盖的组合，补充为新风险条目，标注：**【跨类-Step2.5】**

### B. 信息系统风险动态推演

**不使用预设检查清单。**

基于 my-config.md 中记录的**该公司实际 ERP/MES 等系统**和本次审计主题，推演所有高风险主数据域：

**推演逻辑**：
```
对该公司使用的每个系统模块，思考：
→ 该模块中，哪些主数据的被篡改或错误配置，
  会对本次审计主题产生重大影响？
→ 这些主数据的维护是否存在权限边界模糊、
  变更缺乏审批、日志不完整等控制缺陷？
```

**输出要求**：
- 列出所有高风险主数据域及核心关注点
- 若 Step 2 已识别，标注"已覆盖于 RXX"，不重复
- 未覆盖的补充为新风险条目，标注：**【ERP主数据-Step2.5】**
