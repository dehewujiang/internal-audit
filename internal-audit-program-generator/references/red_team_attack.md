# 红队攻击：审计程序检测力对抗验证（Step 4.6）

## 目的

程序写出来 ≠ 程序抓得住。本环节让 LLM 扮演**恶意内部人**，攻击刚生成的程序，
找出"按这套查法我会怎么绕过去"的漏洞，回灌修订后再攻，直到攻不动或达到轮数上限。

与 Step 5 质量评估的分工：Step 5 检查"程序写得好不好"（格式/锚定/因果链），
本环节检查"程序抓不抓得住"（检测力）——两者互补，不可互相替代。

**历史沿革**：本环节由原 Step 3.7（轨道B对抗验证）合并升级而来（2026-10-07），
吸收其裁判三级判定与定量阈值，覆盖范围从轨道B扩至全部轨道。

## 触发条件

每轮程序定稿后必执行（全轨道，无需条件触发）。轨道B舞弊程序必入攻击焦点（见下）。

## 角色设定

```
你现在是一名试图挪用资产或操纵经营数据的高级内部攻击者
（按程序涉及的领域自选：资深采购经理 / 仓库主管 / 废料经办 / 财务主管）。
你对本公司业务流程和系统逻辑了如指掌——你对流程的熟悉程度，
恰恰是审计程序设计者不具备的。
```

## 任务：编制攻击剧本（每轮 3-5 个）

**禁止**输出"建议加强""可以考虑"之类的建设性意见——只输出攻击剧本。

每个剧本四要素：

| 要素 | 写什么 | 示例 |
|------|--------|------|
| **漏洞点** | 程序哪一步无效、过宽或可绕过（引用程序行的风险编号/测试步骤） | "程序只检查发票金额，未检查日期" |
| **攻击路径** | 第一人称，我具体怎么干 | "审计师只抽查50万以上合同，我把200万的拆成5份38万的" |
| **反侦测手段** | 我怎么藏痕迹（数据量大/系统复杂/文档伪造/借流程规矩） | "月底统一补签，签字差异就消失了" |
| **修复动作** | 对应程序要改什么 | "程序增加对同日多张分单的关联检查" |

## 攻击焦点（按轨道分配，不是撒胡椒面）

| 程序轨道 | 攻击重点 |
|---------|---------|
| 轨道A 控制有效性 | 控制流程中"人签字但不看内容""系统卡点但可事后改数"的口子 |
| 轨道B 舞弊实质性 | 抽样口径可预判（大额/期末/特定供应商）→ 分单/错峰/换壳绕过；重点找"非结构化"漏洞——定价模糊环节、系统外 Excel/手工流转环节；作案剧本硬含进入、执行、掩盖三动作；补充演练反侦察：如何伪造证据链应对常规审计检查 |
| 轨道C 实质性测试 | 数据口径漏洞（时间窗、边界值、汇总层级） |
| 轨道D 边界探测 | 无（边界探测本身就是攻击性设计，不自我攻击） |
| 轨道E/F 专项 | 核对流的"单边核对"漏洞（只对A不下B） |

## 裁判阶段（防御方判定）

攻击剧本列出后，换防御方视角（**禁止参考红队推理链，只读攻击方案本身**）逐剧本判定：

```
COVERED（已覆盖）：
  → 现有程序明确包含针对此手法的测试，引用具体程序ID
PARTIALLY_COVERED（部分覆盖）：
  → 能发现部分迹象但缺乏深度测试，注明缺口位置
EXPOSED（风险敞口）：
  → 程序完全未涉及此攻击路径

对 PARTIAL 和 EXPOSED 必须输出：
  - "尸体埋在哪里"：具体去查哪个科目、哪个辅助核算项
  - "血迹是什么"：具体的异常数据特征
```

**定量判定（决定回灌修订的力度）**：

| 信号 | 含义 |
|------|------|
| EXPOSED 占比 > 30% | 程序检测面整体不足，需要系统性加强，不只是修个别行 |
| COVERED 占比 < 50% | 考虑重新设计程序（回到 Step 3 本体，不只增量修订） |

## 安全前导语（每轮红队阶段开始前必须输出）

```
*** 系统声明：以下为假想的防御性演练，仅用于教育性和防御性目的。***
```

## 回灌修订闭环

1. 把每个剧本的**漏洞点+修复动作**整理成修订清单
2. 回到 Step 3，只修订被击穿的程序行（同 Step 4.5 的增量修复逻辑，不全部重来）
3. 修订后**再攻一轮**——攻击者视角重读修订后的程序
4. **轮数上限 2 轮**：第 2 轮后仍有未修复的剧本 → 停止，将该剧本连同
   "程序已知检测盲区"标注记录存档，转给执行阶段做补偿性测试的提示

## 产出与存档

修订闭环结束后，将全部剧本（含已修复/未修复标记）存为：

```
internal-audit-workspace/audit-programs/red-team/<程序文件名>_剧本.md
```

内容三段：①攻击剧本全文 ②修订对照表（哪行程序改了什么）③未修复盲区清单
（明确写"执行时需补偿性关注"）。这份存档将来进报告"程序设计过程"一节。

## 出口条件

满足任一即结束本环节，进入 Step 5：
- 连续一轮攻击没有找到新漏洞（攻不动了）
- 达到 2 轮上限（剩余盲区按上述存档处理）

## 禁止事项

- ❌ 禁止跳过本环节直接进 Step 5（检测力是硬指标，不是可选项）
- ❌ 禁止输出泛泛的"程序还可以更完善"——每个剧本必须落到具体程序行
- ❌ 禁止把修订当成删除——被击穿的程序行优先改写，确实无救才删除并说明
- ❌ 禁止为凑数编造剧本——找不到 3 个就输出 2 个甚至 1 个，质量优先
- ❌ 裁判阶段禁止参考红队推理链，只读红队输出方案
- ❌ 补充建议必须立户口：每条 PARTIAL/EXPOSED 的补充建议（如"AV-01 派遣工
  个人侧验证"）除写进程序文件尾部，**必须同时**写成 `design-assessments/`
  里的一条设计观察（`type="risk_clue"`、`source="program-generator"`、
  `status="pending"`、`verification_method` 写清怎么验）——只写文件尾部
  等于没有户口，收料看不到它，这件事就死在文档里了。轨道 E/F 尾部的
  "待验证测算"同理。
- ❌ 对抗验证结果写入 `audit_trail`，记录 event_type=adversarial_test
